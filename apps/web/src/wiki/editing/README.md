# V7.1 章节编辑与发布快照

阅读页给编辑器传递明确的对象、章节、内容模式与返回位置。用户可以从正在阅读的段落开始，不需要先去贡献中心理解数据归属。

## 阅读页接口

```jsx
import EditEntry, { PublishedSection } from "./editing/EditEntry";

<EditEntry
  entity="海芙约忒"
  section="获取时间线"
  mode="acquisition"
  record="haifu-20240705"
  returnTo="/pets/haifu/#acquire"
/>;
```

`intent="add"` 表示新增。省略 `record` 时编辑整个记录集合；指定稳定记录 ID 时只编辑对应记录。新增活动开放批次仍然打开同一个活动主条目，原有批次留在表单和差异基线中。

`editorHref()` 生成以下地址。`entity` 和 `section` 是阅读标签；`mode` 决定表单；`returnTo` 只能是站内地址。保留宠物技能池、筛选结果和具体锚点的返回上下文。

```text
/edit/?entity=海芙约忒&section=获取时间线&mode=acquisition&record=haifu-20240705&returnTo=/pets/haifu/%23acquire
```

实际链接由 `URLSearchParams` 编码，不手工拼接。兼容旧的 `from`、`action=create`、`counter`、`skill-effects` 参数。

## 表单归属

| 模式           | 内容                                                       | 基线来源                                     |
| -------------- | ---------------------------------------------------------- | -------------------------------------------- |
| `article`      | 对应小标题下的 Markdown 正文                               | 当前文档和阅读页章节快照；计算规则有单独原文 |
| `acquisition`  | 获取名称、起止日期、条件、地点、奖励、来源、活动和批次关联 | 宠物获取历史记录                             |
| `event`        | 活动主条目、简介、历次开放批次                             | `events-v7.json`                             |
| `skill`        | 技能描述、基础资料、基础效果、条件分支                     | 与读页相同的技能展示数据                     |
| `matchup`      | PVP 对手、上场情境、结论、条件、例外、日期、来源           | PVP 对位记录；没有 PVE 分栏                  |
| `npc`          | 人物名称、别名、出现场景、职责、介绍、服务、任务、来源     | 人物数据；新增打开空表单                     |
| `pet`          | 宠物身份、筛选属性、六项种族值                             | 宠物资料与补充字段                           |
| `pve`          | 挑战对象、宠物、版本、配置、操作、替代与证据               | 副本资料及迁移后的历史挑战记录               |
| `index`        | 目录名称、入口、用途说明                                   | 对应目录的站内记录                           |
| `relationship` | 已有与新施加来源、方向、时点、条件、结果、复现证据         | 新建实测表单；现有文章通过正文编辑           |

技能 `record=base` 聚焦基础效果，`record=branch-1` 等聚焦一个条件分支；添加分支保留原技能参数。已有记录中的 `otherwiseWhen` 不能被简化为无条件“否则”，因为它可能对应另一种明确的技能类型或场景。

PVP 新记录必须主动选择上场情境。来源没有说明时，可以明确选择“尚待核实”，不能强迫编辑者从同起、后上拦截、先在场中猜测一个。已有方向描述只在其对应的情境未改变时继续使用。

## V7.1：具体条目与只读阅读预览

目录页面不再提供可修改全部条目的通用表单。宠物目录只能新增宠物，既有宠物进入详情后修订，删除通过 `intent="delete"` 提交单只宠物的提议。发布后的删除使用 tombstone，保留历史引用，不连带删除技能和其他资料。新增宠物的稳定 `slug` 在投稿时分配；本机详情通过 `/pets/?entry=<slug>` 访问，改名后仍以稳定标识定位。历史获取和 Counter 通过 `catalogNames` 保持名称变更前的记录连续性。

地区的“补充地点快捷入口”仍使用 `index`，但新增基线为空、每次只有一条入口，并校验目标为 `content/routes.json` 已有地点路由。它不能新增一个虚假的地区详情页，也不能在一份投稿中编辑整个目录。

编辑器现在有三个独立视图：填写与修改、预览效果、对照差异。十一种编辑模式均有按阅读语义绘制的预览，不把序列化字段差异作为阅读效果。知识文章复用 `ReadingMarkdown`，宠物复用六维图，技能复用 `SkillEffectFlow`，PVP 复用 `CounterBloodlineSides`，PVE 复用 `PvePlanCard`；新增玩法使用 `PveGuidePreview`。

`ReadPreviewFrame({mode, data, context, intent})` 将只读组件渲染到同源空白 iframe 的 React portal 中，复制当前样式并提供桌面和 390px 手机内容宽度。媒体查询因 iframe 自身宽度而变化，不是单纯压缩外层容器。预览不写入 localStorage，不传编辑或投票操作，链接点击也不会带走未完成草稿。它预览的是当前内容范围，而不是完整站点外壳。尚未做真实浏览器截图与设备性能验收。

### V7.3：阅读方向和预览生命周期

技能流程提供纵向、横向两个选择，偏好只属于当前这一组流程。实际内容区域不足 760px 时，横向偏好临时按纵向展示，并说明加宽后会恢复横向；Mermaid 按当前实际方向导出 `TD` 或 `LR`。方向变化只改变布局，不改变判断条件、效果节点或边的语义。阅读页和编辑预览使用同一个组件。复制 API 的异步结果有请求代次检查，切换方向或卸载之后不会展示过期的复制成功状态。

预览高度订阅集中在 `previewRuntime.js`：以当前 iframe、文档和 React 容器作为同一代生命周期，字体就绪、图片载入、窗口与内容尺寸变化统一合并到下一帧测量。取消订阅时断开观察器、事件和待执行任务；旧文档的字体 Promise 即使稍后完成，也不会重写新文档的高度。样式每个文档只复制一次，切换预览宽度不会重建文档或 React 容器。超长内容的 iframe 高度有上限，并提示在框内继续滚动。

`PreviewBoundary` 分别保护阅读内容、预览壳和技能流程。发生渲染错误时，显示错误位置、可展开的错误信息及“重新显示”，保留母页面的编辑器状态；修正数据也会自动重新渲染。错误事件通过 `roco:render-error` 发出，重试本身不会覆盖草稿。

`validation/v73-preview-before.json` 留存修复前的源码摘要和 DOM 复现结果；`validation/check-v73-flow.cjs` 复测旧字体回写、iframe 内容异常传播、StrictMode 挂载清理、多次切换设备、方向与 Mermaid 一致性、图片后加载以及局部恢复。这里确认的是源码与 JSDOM 缺陷和修复，未将它们断言为用户报告的真实设备黑屏的完整原因。

## V7.1：可组合的技能条件

`phases` 仍是旧数据的兼容入口。每个分支保留原 `label / when / effect / otherwiseWhen / otherwise` 字段，增加 `conditionTree`、成立后的 `children` 和可选 `otherwiseBranch`。规范化不会丢弃旧字段或自定义元数据。

```js
{
  label: "第 2–5 回合的条件效果",
  conditionTree: {
    kind: "group", operator: "all", children: [
      { kind: "rounds", basis: "skill-sequence", mode: "ranges",
        ranges: [{ start: 2, end: 5 }] },
      { kind: "group", operator: "any", children: [
        { kind: "clause", text: "来源中的条件 A" },
        { kind: "clause", text: "来源中的条件 B" }
      ] }
    ]
  },
  effect: "条件成立时按来源执行的效果",
  children: [],
  otherwiseBranch: { conditionTree: null, effect: "来源明确的否则效果", children: [] }
}
```

回合范围支持单序号、连续范围和多个不连续范围；模板覆盖 `1 / 2 / 3`、`1 / 2–5 / 6`、`1–2 / 3 / 4`、首／中／末及首／后续。模板只追加空效果结构，保留已有内容。每个范围必须明确计数依据：连续技能内、整场战斗、技能使用次数、效果持续回合或自定义。来源未说明时保留文字条件，不自动推断为某种计数。

校验拒绝非正整数、反向范围、单个条件内重叠，以及同一明确分段模板的纯回合范围重叠；一般条件可能同时成立，只给出核对提示。`all / any` 条件最多嵌套 6 层，效果分支最多嵌套 5 层。这里存储和展示有来源的规则，不模拟游戏结算，也不自动证明复杂分支是否互斥或完备。

## V7.1：双方本场血脉

Counter 使用 `myBloodline` 和 `opponentBloodline`，均为 `{ status, names, note }`。`status` 为 `unknown`（未记录）、`none`（明确未携带）或 `specified`（已知本场血脉）。宠物种类可拥有的血脉不等于本场实际携带的血脉，不能自动填入。

双方配置同时进入结论指纹，改变血脉配置后统计归属于新命题；仅调整血脉名称输入顺序不会换票池。读页与编辑预览复用同一双方配置组件。数据、源码和公开投票仍是本机体验；真实统计和身份由既定后端负责。

## “当前发布版本”的精确含义

本原型没有连接线上 API。首次进入编辑器时，基线来自**随当前站点版本一同交付的实际资料**，不是 `demo-r17` 占位文字。文档基线保留原始 Markdown，小标题只加载本节正文。获取、技能、对位等读取与阅读页相同的数据。

`pub-xxxxxxxx` 是前端对规范化内容计算的指纹，方便本地识别是否变化；它不是 Git 提交 SHA，也不是安全令牌。上线服务必须使用服务端签发的版本标识（如 Git tree/commit SHA 加章节修订号或 ETag），不能将这个短指纹用作服务端并发控制。

完成本地审核、普通合并、构建和模拟发布后，已发布记录成为本浏览器下一次编辑的基线。页面明确显示“本机已发布版本”。这不意味着线上仓库、账号或静态站已同步。

## 草稿、提交与冲突

草稿保存 `editorRequest`、`snapshotKey`、`baseVersion`、`baseData`、`baseContent` 和 `typedData`。切换页面或关闭页面前会保留尚未保存的修改。个人中心“我的投稿 → 草稿”使用同一定位参数恢复。

投稿携带实际修改前后内容。审核通过之后仍然需要普通合并、构建、发布；各阶段独立保留。合并前再次核对基线，版本不一致时进入冲突状态。模拟上游冲突会创建真正可读取的本地新版，便于完整体验后续流程。

对比采用三方数据：开始编辑时的基线、当前发布数据、自己的草稿。不同对象字段可合并；同一字段双方都修改过时必须选择采用当前版本还是保留草稿。记录数组发生并发变化时作为一个冲突项处理，不会静默删掉别人新增的行。该保守策略适合演示和小集合；正式服务可进一步按记录 ID 做逐行合并。

## 阅读页与编辑器共享本地结果

`resolvePublishedRecords()` 按发布时间依次应用获取和 PVP 对位的整节替换、单行编辑、单行删除与新增。待审核记录不会影响阅读页。目录读页与编辑器复用这个解析器，因此从整节或单行入口进入都能看见相关最新数据。

PVP 对位内容改变时生成新的 `claimRevision`。未改动的其他记录保留自己的版本和票池，换行字符串与等价条件数组不应被误判为新的结论。投票统计与编辑字段分离，投稿者不能填写或修改支持率。

活动以 `mode + activity.id` 共享一个发布快照。批次 ID 只决定表单聚焦位置，不将一次返场拆成另一个活动。草稿另含具体入口和新增意图，避免误恢复不同操作。

`composePublishedDocument()` 按发布时间组合整篇和分节投稿。整篇修订可以更新随后打开的小节基线，小节修订也会进入整篇基线；待审核投稿不参与组合。编辑器和原生 Docusaurus、预览阅读页共用这套组合规则。基线版本按当前编辑范围的实际内容计算，其他小节的单独变更不会让未改变的章节产生冲突。

`usePublishedSection(request)` 可取得本机已发布的 `snapshot.data`。`PublishedSection` 的文章模式直接使用安全 Markdown 渲染器替换原正文，并显示本机版本提示；结构化页面由各自的数据解析器显示最新字段。发生本机状态变化时发出 `roco:community-updated` 事件，其他页面组件可以即时刷新。

新增人物经过本地审核发布后出现在人物目录，并通过 `/npcs/?entry=<稳定标识>` 打开本机条目；继续编辑读取其已发布字段，名称修改不会使原标识失效。正式站点的静态路由仍需发布服务产生数据并通过构建后上线。不能把本地状态标记误解为生产环境已建立新页面。

## 生产接口接入

现有既定架构继续采用独立 Wiki 账号、可选 GitHub OAuth、Workers/Hono、D1、GitHub App、每次投稿独立提交及普通合并；不改成 squash。GitCode 保持单向镜像，EdgeOne 分发静态站。

生产服务应提供以下能力，前端字段可以直接映射；此版本没有调用这些 API。

```http
GET /api/wiki/entries/{entryId}/sections/{sectionId}
POST /api/wiki/drafts
POST /api/wiki/submissions
GET /api/wiki/submissions/{submissionId}
POST /api/wiki/submissions/{submissionId}/review
```

读取章节返回规范数据、稳定 ID、字段 schema、当前发布版本、编辑权限及引用记录。请求只能选择服务器已知 schema，不能上传可执行脚本或任意 MDX。公式文章可以走贡献审核，计算实现的变更仍需代码评审和算例验证。

提交请求至少包括稳定对象 ID、章节 ID、记录 ID、`baseRevision`、字段改动、摘要与来源。显示名和小标题可以变更，服务端身份不能只依赖它们。目录新入口还要校验目标路由、重复对象和关联完整性。

服务端在草稿保存、提交、审核与合并时分别验证身份与权限；浏览器里的体验身份按钮不构成权限。GitHub 署名只在用户授权后加入，每次修订都保留作者、来源、基线和对应独立提交。
